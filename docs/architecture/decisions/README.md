# Architecture Decision Records

These records explain consequential engineering choices: the problem, the
selected boundary, its tradeoffs, and the alternatives it rules out. Platform
contracts remain normative when an explanation disagrees with them.

Use the [generated component index](../ARCHITECTURE_COMPONENT_INDEX.md) to find
records by subsystem, component, status or implementation path. It is the
exhaustive catalog; this page does not maintain a second inventory.

An accepted decision records architectural direction within its stated scope.
It does not certify every implementation, release or deployment. Draft records
must state their qualification boundary. Dated implementation observations are
evidence about that source, not a continuously renewed readiness claim.

Read a historical decision with its amendments and linked successors. Preserve
the original reason for a choice when a successor changes part of it; identify
the superseded scope near the beginning instead of forcing readers to discover
it in another file. Existing identifiers, including duplicate numeric prefixes,
remain stable. Cite the descriptive title or filename when a number is ambiguous.

New records should explain a durable change to ownership, lifecycle, accounting,
causality, recovery, security or another consequential boundary. Routine file
moves, qualification diaries and current operational status do not need ADRs.
Use the [documentation standard](../../engineering/documentation/component-documentation-standard.md)
and current subsystem docs for implementation navigation and operating procedures.
