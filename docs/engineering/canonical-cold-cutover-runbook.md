Prepare and rehearse one controlled switch from the live PostgreSQL and Parquet layout to the cold canonical layout. Production writes, collector interruption, replacement activation, and source retirement require the final operator decision on the exact rehearsed operations and candidate release.

## 1. Establish independent recovery and restoration

Designate an authorized storage target outside the QT server and a disposable restore target. Restrict access to the operator and keep recovery keys separately retrievable. Record measured available bytes and stable mount/device identity on each target. A USB disk attached to another host can supply a separate failure domain for the cutover. Retain the local generations until the independent point is readable and tested.

Size the repositories for the current database backup, WAL, exact archive inventory, and temporary overlap. The current local repository allocation of 2.89 TB is a planning anchor. Account for a possible full baseline, WAL until completion, other retained recovery points, and verified filesystem reserve. Budget the isolated restore separately. The November 14 PostgreSQL layout alone needs roughly 1.26 TB on the old hot device and 0.60 TB in the historical tablespace, before raw/archive objects, replay WAL and workspace. Where repositories and restore share a device, sum concurrent peaks. Measure destination throughput, repository growth and peak allocated space on the representative rehearsal.

Use the [paired recovery protocol](../architecture/decisions/0072-use-encrypted-incremental-recovery-sets.md) and its compatible pgBackRest and Restic versions. Capture a physical database backup and a hash-verified Restic inventory under the archive-expiry fence. Pin the database identity and timeline, exact backup label and earliest consistent endpoint, full backup chain and required WAL, archive snapshot ID and inventory SHA-256, serving roots and tablespace mappings, tools, application release and source commit watermark.

The existing `storage_recovery_prepare.py` prepares the fixed local target. For a remote target, qualify the coordinated off-host export or remote configuration with the same recovery checks. If exporting an independent copy of a local native repository, hold pruning and capture every named dependency before sealing the external receipt. Do not copy live PGDATA with filesystem tools or replay beyond the paired endpoint without a separately verified matching archive set. If the full copy precedes the final provider handoff, retain an independently verified incremental or append-only delta and prove bounded replay into the restored old release. Every accepted fact through the writer fence has to be present in the independent point or exactly once in that validated delta.

Restore the named pgBackRest backup to its immediate consistent endpoint, remapping tablespaces away from production. Restore the matching Restic snapshot, verify the inventory checksum, and verify the hash and length of each referenced restored object. Start PostgreSQL with the matching extensions and pinned original application on an isolated network or socket, with production endpoints unreachable. Verify the catalog, table and manifest identities, ordered source content roots, frozen membership and digest, latest and as-of boundary reads, and raw-backed book reconstruction. Verify stream prefixes and pending-segment recovery. Detect a missing or corrupted object and interrupt a rehearsal restore without affecting the completed independent point. Record wall clock, peak allocations, verified paths and tool versions. A successful small fixture exercises the tools. Actual qualification also needs the representative paired recovery and candidate rollback on that restored data.

Use `python scripts/automation/verify_canonical_recovery_archive.py --receipt <independent-complete.json> --restore-target <isolated-restic-restore-root>` to verify the exact Restic inventory and every named archive object's size and digest against the receipt. Capture its JSON output with the PostgreSQL restore and application receipts. This verifier addresses the archive half and uses no live server connection. Run it on a quiescent isolated restore with no other writers.

## 3. Rehearse replacement and rollback

Use the [checkpointed staging and inactive catalog procedure](canonical-cold-staging.md) for exact tool invocations and disposition rules. A completed catalog load cannot authorize retirement. Verify raw and derived dependency closure, retained pins and all accepted versions at the actual source boundary.

Convert the dataset off the writer fence or on the isolated production-size restore. Generate an immutable candidate receipt with named relations and object generations, source watermark, ordered row/identity roots by family and interval, candidate inventory and checksums, affected frozen references, tolerated existing gaps and dependency disposition. Deploy against that isolated data in the same order planned for production. Exercise current writes and corrections, historical intake, mixed and frozen reads, raw-backed replay, archive and retention jobs, and downstream consumers under representative concurrency. Verify that no runtime read, write, foreign key, scheduled job, or export still needs each retired relation across restart. Measure actual source and replacement allocations and per-step elapsed time, with writer-fence time measured separately from off-fence copying.

Preserve source bytes required for custody, immutable accepted versions and their clocks, lineage, and frozen membership. Selective reacquisition can fill currently incomplete provider coverage and support regenerable derived data once inputs and transformation identity are proven. Regenerable indexes, caches and optional projections may be rebuilt from equivalent preserved inputs. Count capacity only for named physical objects whose source preservation and retirement have been qualified. Never infer a whole file is eligible from an average row size or provider's candle availability.

| Rollback boundary | Rehearsal |
|---|---|
| Before new authoritative writes or source retirement | Switch serving back to the pinned old release while retaining old files and artifacts. Compare old watermark and source roots, then reconcile pending provider spool once under the old writer contract. |
| After new writes or source retirement | Restore the independent paired point into separate storage and replay every accepted post-watermark operation exactly once with its original identity and availability. Verify the pinned old runtime and frozen/as-of results before switching back and resuming collection. |

Prefer parity with writers fenced before the serving switch. Retire the source after the recorded soak and read/live parity. If the new writer begins before retirement, retain a durable delta with an old-format replay path for the entire rollback interval. If the chosen rollback cannot be demonstrated, keep the old files and end the window on the old release.

## 4. Produce the final command sheet

The current branch provides preparation, exact bounded audit and readback primitives. The final writer-fenced transition and steady-state retirement of both hot payload and SQL header/identity custody still require implementation and recovery rehearsal. The old payload-only drop is refused under the candidate layout so it cannot reintroduce an unbounded directory. An inactive catalog and passing component tests do not grant production authority.

Prepare a single approval record from the successful rehearsal. Pin current and candidate image IDs, exact commands and order, responsible operator and writers, expected and maximum downtime, affected streams and polls, limits and abort boundaries, exact source retirement scope, recoverable watermarks, paired backup receipt and independent restore results, destination capacity/overlap, and tested command paths for both rollback branches. Include checks for unintended old-relation access, backend/collector health, pending spool, early backup refresh, actual SSD block return, and what isolated evidence to compare on every retry.

Material changes in runtime, or failed capacity, watermark, source-integrity, restore or parity checks, halt progression at the next intact boundary. Record actual downtime, affected data intervals, actual filesystem block return, completed recovery point and remaining exclusions in the final receipt. The checked-in boundary inspection is executable. The production command sheet still depends on the qualified independent destination, candidate rehearsals and exact source-specific operations.
