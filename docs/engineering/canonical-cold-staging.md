# Stage canonical history for the one-time cutover

Use a separate, current recovery pair and disposable PostgreSQL restore for rehearsal. Run the source read against the old application/schema revision. The tool stages immutable Fact archive pages and writes a local progress inventory. Source retirement requires the integrated cutover procedure and its fresh checks.

## Staging one cohort

Use the existing `PG_DSN` and provide the expected PostgreSQL system identifier from the approved recovery inventory. Staging works on one physical `storage_day` at a time. The day must have a retention row with a sealed source count. That includes reclaimed payload days for which the immutable SQL headers and all corresponding archive manifests still exist. Inventory legacy days by their authoritative storage day; the archival tool does not infer them from observation date or file age. An absent or open day needs explicit source reconciliation before staging.

```text
python -m scripts.db.canonical_cold_migration \
  --source-system-identifier <expected-id> \
  --day 2026-09-28 \
  --source-object-root /rehearsal/archive/objects \
  --staging-object-root /rehearsal/stage/objects \
  --temporary-directory /rehearsal/stage/work \
  --checkpoint /rehearsal/stage/progress.sqlite3 \
  --max-pages 1 --max-seconds 120
```

Repeat the command with the same checkpoint to resume. The checkpoint binds the source system, database and parent relation identities, the physical day, seal timestamp, expected count, initial archive prefix, source and destination roots, and codec limits. Each page advances a keyset cursor only after verified bytes and full source comparison. A missing staged object is caught by `verify_completed_cohort`; keep the source and a second valid copy until that check and the integrated gate have passed. Reuse-in-place is available for an explicitly approved shared object root via `--reuse-in-place`. Distinct roots copy the same content-addressed bytes. A new object may remain staged after an interruption before journal commit. Re-running the exact page can reuse those bytes.

On the deployed generation-aware schema, a reused page records whether it has an active prepared generation or an older published catalog. The active pointer must agree with the published manifest, preparation state, source binding, actual ordered prepared catalog roots and batch commitment. Current verification receipts, where present, must match that authority. An older published page or a page pending current verification can still reuse the exact object after source and byte comparison. Its checkpoint explicitly carries no current verification claim. The mounted bytes remain unchanged. The final audit repeats repository authority checks and refuses changed generation bindings or newly overlapping source pages. Reconcile those changes in a fresh approved journal using the same immutable objects. Rebuild only where a new source page is actually needed. This journal format requires a v2 checkpoint and preserves neither raw lineage authority nor approval to retire the SQL source on its own.

SQL reads use short repeatable, read-only transactions. Each transaction limits server-side statements and lock waits. The wall budget is checked between pages. Individual encoding or file writes can run past the elapsed budget after a page starts. A completed cohort records exhaustion and the exact sealed row count. `MigrationCheckpoint.iter_completed_pages()` yields only completed cohorts and includes the prior exclusive source cursor, manifest descriptor with object key/hash, and whether it was reused. `verify_completed_cohort()` checks current staged file contents, ordering, counts, and checkpoint membership without an SSD cache. Depend on the paired source snapshot and a separately verified final owner fence for serving activation.

## Prepare the cold catalog

Install the cold schema and registered HDD tablespace first. Configure the target layout's archive root so its `objects` directory is the checkpoint's staged object root. With `PG_DSN` set to the approved target database, supply its current system identifier, database name and OID separately. A mismatch stops the command before any catalog admission.

```text
python -m scripts.db.canonical_cold_load \
  --target-system-identifier <target-system-id> \
  --target-database <target-name> --target-database-oid <target-oid> \
  --day 2026-09-28 --checkpoint /rehearsal/stage/progress.sqlite3 \
  --max-pages 1 --max-seconds 120
```

The loader validates each page's current mounted bytes through the serving codec, acquires a state-table lock and checks for an inactive cold layout before each admission transaction. It never changes that layout flag or source relations. Record `last_processed_ordinal`. On retry, reread the same page idempotently or provide `--after-ordinal` with the previously committed value. An end-of-checkpoint receipt only describes the batch traversal. The activation procedure must verify every page, loaded memberships, dependency holds and the final writer fence independently.

## Verify the retiring prefix and prepared catalog

`python -m scripts.db.canonical_cold_audit` takes the same database identity and checkpoint arguments as the loader. Add `--cold-before-day <first-retained-day>` to print the bounded audit scope. Its plan uses the first matching source row and the registered dated physical children. The legacy range must be intact, so the cutoff cannot split the legacy relation.

For **every** day in the resulting oldest prefix, run `--day <storage-day>` and capture the receipt. A nonempty day needs a completed migration checkpoint. The audit decodes each current HDD page and checks the exact Fact identity, observation key, revision, commit and row hash against the source row, global identity registry and loaded ordinal. It also checks actual source child OID and loaded series bounds. A retained row for the same series must have a later commit, and a retained row for the same exact observation key must have a higher revision. Retain `--after-ordinal` and the matching preceding receipt for subsequent batches. Compare the sum of pages and rows with the day counts and require traversal from ordinal zero through the recorded source tail.

Separately, scan `--inverse-inventory` from the beginning through `inventory_scan_end_reached`, advancing with `--after-manifest <last_verified_manifest>` to detect an unexpected loaded page. All receipts must agree on `prefix_hash`, checkpoint binding hash and database identity. Missing receipts, skipped pages, lookup discrepancies, an unmatched loaded manifest or nonempty uncheckpointed day halt progression. These read-only transactions do not freeze writers or hold a production fence between batches. Reconcile the full receipt set under the final owner fence and qualify the independent paired restore, raw and L2 coverage and holds, frozen/as-of reads, remaining relation dependencies, and physical retirement separately. The audit emits `activation_ready: false` even after a successful bounded batch.

Save every forward and inverse v2 receipt in one JSON array and run `python -m scripts.db.canonical_cold_receipts <audit-receipts.json>`. The validator checks the exact plan, database and checkpoint bindings, per-day seal and state, all sequential row/page cursors and counts, and equality of forward and inverse manifest inventories. The output includes the retired prefix's maximum observed commit, observed per-day totals, and the complete `audit_set_hash`. Pin that digest with the approved inputs and keep the original receipts. The final owner's fresh catalog comparison streams the `loaded_inventory_hash` over `[manifest_id, manifest_hash, row_count]` in ascending manifest ID order. The `inventory_hash` additionally binds the audited source days. Consolidation supplies evidence for the gated transition and does not perform activation.

## Data decisions

| Inventory evidence | Disposition |
| --- | --- |
| Accepted Fact version, frozen pin, custody hold, or hard-to-reconstruct dependencies | Give the existing source bytes and all revisions an exact durable placement. Keep reception, acceptance, availability, revisions, external keys, quality and provenance. This includes captured raw stream inputs, receive ordinals, L2 snapshots and deltas, checkpoints and dependent artifacts. |
| Provider-native Coinbase historical candle gap with explicit missing coverage and no accepted/held evidence for that range | Reacquire under its own run once provider product coverage and retained source meaning are established. Compare boundary overlap against existing exact versions, record empty intervals and errors, and use QT's admission rules for new observations. A provider value match supplies no evidence about QT's earlier availability. |
| Rebuildable cold locator, typed candle projection or read cache with verified source inputs and no independent identity/custody | Rebuild from authoritative inputs and verify its output, exact lookup and eviction/failure behavior. A legacy SQL index used by a still-active caller stays until the replacement has proven coverage and that caller has migrated. |
| Ambiguous operator history, stale retention evidence, unresolved hold, or unsupported contract | Preserve exactly and escalate the missing evidence before changing its lifecycle. |

QT's advanced-trade adapter requests at most 300 candles and advances by 299 intervals to account for a provider that may include both endpoints. Coinbase's current public product-candle endpoint documents a maximum of 350. Planning uses the installed adapter's observed behavior. Five 365-day years for one symbol need at least 8,790 requests for 1m, 147 for 1h, or 7 for 1d, before retries, coverage holes and any product retention limits. Ten symbols at 1m need at least 87,900 requests. Count each requested half-open contiguous window separately. Window data or count parity does not establish accepted-row parity. Benchmark the same API product and adapter away from production, with the same no-trade and error handling. Record successful ranges, throttling, elapsed publication, gaps, and capacity effects before using any ETA or replacing copy work with a provider workflow. BTC-USD minute windows in October 2021 and October 2025 and an ETH-USD hourly window in October 2021 each supplied all 299 in-window bars. BIP-20DEC30-CDE hourly requests in October 2025 and November 2026 supplied 297 and 298 of 299 respectively. All five returned HTTP 200 and an additional closing-boundary candle, which QT excludes. Observed request times ranged from 154 to 227 ms. A missing bucket still needs its own coverage classification. The spot and futures sample measures connectivity and returned buckets only. Sustained throttling, product history limits, exact overlap against accepted rows, and publication time need separate measurement on the selected gap inventory.

### Cutover recommendation for Coinbase history

Reuse verified archive bytes and move only the accepted versions still missing a durable placement. Limit provider work to verified missing coverage and reproducible derived work whose original inputs and transformation can be reproduced. A provider version matching the same OHLCV values may have a different source revision, acceptance time or causal availability. It also cannot fill the replay gap between two Level 2 connections or attest to QT's raw receive ordinals.

The November 14 live PostgreSQL statistics estimated candles at **2.97% of legacy header rows** and **1.25% of the November 13 dated header rows**. These include derived candles and other candle lineage as well as native historical Coinbase captures. Three quarters of the legacy sample was Level 2 and depth observations. These are analyzed row estimates from `pg_stats` and do not attribute bytes or authorize retirement. The **382.21 GB** legacy header is a single attached PostgreSQL relation with its indexes. Removing a candle subset has zero guaranteed filesystem credit. Both strategies ultimately require a verified replacement and retirement of the same physical relation. Existing archived candle pages can often be reused without decoding a new provider response or waiting for its history windows. A measured cold copy/resume pilot is therefore the primary schedule input.

| Method | Reclaim and time basis | Qualification |
| --- | --- | --- |
| Reuse bytes plus exact copy | Read verified HDD pages and compare retained envelopes. Encode only uncovered accepted rows. Measure complete validated rows/hour and target catalog growth on the restored hardware. Credit blocks only after approved drop of the exact source relation. | Preserves versions, clocks and proof. Current hashes, external holds and frozen replays remain mandatory. |
| Provider reacquisition | Request budget is a lower bound. Measure complete windows/time, retries, product reach, and publication separately. Do work outside the writer fence. No standalone SSD credit for the provider leg. | Fresh observation uses its own run. Compare overlaps, disclose holes and preserve prior accepted versions. |
| Rebuild disposable data | Delete or replace named full physical units only after validating inputs, deterministic transformation/output, and absence of custody. Track cache or index allocation independently. | Retain exact evidence for any derived result that is a canonical version or frozen input. Standalone projections and caches can be rebuilt from verified authority. |

No existing accepted Coinbase datasets are approved for replacement-only retirement. After final qualification, use `qt data ingest-candles --fill-missing-only` with the inventoried instrument, range, and timeframe for native Coinbase gaps outside the hot window. The series writer checks every returned key under its publication lock. Equal overlap is a no-op, and changed overlap fails the whole admitted batch for separate correction review. A new row becomes known at this acquisition's platform acceptance time and goes directly to the cold store. Frozen commit ceilings exclude these later rows. Plan provider work separately from the writer fence and keep any unresolved missing intervals explicit.

## Readback evidence before handoff

Capture ordered, deterministic result streams from the old and new runtime paths using matching source boundary bindings. Use `verify_parity()` on those streams. The required cases cover all revisions, as-of selection, frozen dataset readback, coverage, raw ordinals, L2 replay and raw holds. Include exact versions and hash, decoded clocks and metadata when relevant, invalidation, correction timing, cross-tier boundaries, absent intervals, and lead/successor replay. For frozen data compare current dataset identity, commit watermark, ordered consumed IDs, material/provenance/quality and coverage before comparing higher-level outputs. Separately rehydrate raw records using their exact object hashes and decode ranges, then compare sequence and receive ordinal through each L2 checkpoint or replay witness. Check the inventory of raw and checkpoint holds, including retained frozen, replay and migration recovery generations, before any expiry changes. Restore and verify a separately retrievable pair at the actual boundary.

The harness's output binds its case, source boundary, ordered comparison digest and row count. Scope and input adapters belong to the actual rehearsal. Content mismatch, coverage mismatch, mismatched boundary, an unexpected empty result or an untested required domain fail the gate. A cohort checkpoint alone proves migrated Fact bytes and headers for that cohort. Integrated readback, dependency availability, frozen replay and physical retirement remain separately owned acceptance checks.
