# Compact cold lookup directory design notes

Retain the existing PostgreSQL HDD tablespace and transaction boundary while measuring key compression. One option replaces each repeated page identity string with a bigint foreign key to a unique immutable manifest. It stores generated `mfv_` version IDs in their exact 20-byte form and preserves every other admitted ID in a tagged lossless encoding. The canonical string remains in the verified Parquet envelope and the API. The full 32-byte row and material hashes stay intact. Material index entries can reference the same compact ID. A numeric locator key is a separate experiment because the additional lookup or uniqueness index can erase some savings. Keep scope/evidence-key handling exact for legacy aliases; the simple benchmark includes canonical material only.

The current candidate's locator, material, normalization and book-session heaps, TOAST and indexes must be permanent and on registered HDD storage. Page catalog and per-series summaries are separate and can still grow on the database default tablespace. PostgreSQL still writes WAL for durable HDD catalog changes. Monitor peak allocated SSD WAL and archive backlog, hot tables and the retained hot identity indexes, and any enabled SSD history cache. The earlier native million-row test measured 3.15 GB WAL inserted during serial publication on a shared fixture device. That is generated WAL volume. Actual SSD peak also depends on replication/archival progress, recycle behavior and checkpoint timing.

The exact directory also serves the archive reference trigger, staged-day visibility, rollback membership, header cleanup, commit lookup, normalization and book-session membership, and deciding whether a cold key has a head before an ingestion can claim absence or classify a duplicate. Material hints require exact source row hydration. PostgreSQL key compression keeps these checks in the same snapshot and lifecycle fence while changing only internal storage representation. Requalify plans, uniqueness and trigger access, row hash validation, mixed hot/cold revision selection, archive evidence and DDL rollback before replacing the existing catalog. An online shape migration needs peak overlap, WAL capacity, exact forward/inverse coverage, and a fenced cutover.

A per-page or per-cohort immutable directory file can be built from fully admitted Parquet, with its coverage and hash published only in SQL. Readers would have to bind its versioned inventory to their current SQL snapshot, preserve the selected directory files for the lifetime of that snapshot, enforce checksums, and fail closed when the directory needed to prove absence is unavailable. It does not provide PostgreSQL row-level enforcement to the four live/prepared archive reference checks or make their retirement joins atomic. Replacing those SQL consumers would need a separate approved change. The existing SQLite migration journal is a local checkpoint for staging and a useful precedent for bounded file state. It does not serve write authority or application lookup.

The optional compact benchmark checks exact ID, latest key and material lookups on synthetic paired relations. Temporary tables isolate shape and avoid catalog WAL measurements. It exercises no production page publisher, trigger, row visibility or durable writes.

```sh
bash scripts/db/canonical_cold_scale.sh --compact-directory --rows 100000
```
